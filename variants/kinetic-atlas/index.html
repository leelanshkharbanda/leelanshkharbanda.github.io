02 / SELECTED WORK — DATASHEETS

Three instruments,
one question: what can we verify?

Each entry is a datasheet, not a sales pitch: the mechanism, its stated boundary, and the one detail worth keeping.

DS—01

PROPAGATION

Chronos-DSP

A real-time wireless propagation simulator with an Elixir/Phoenix control plane and a Rust NIF DSP data plane. A LiveView dashboard drives a 3D scene of transmitters, receivers and planar walls while the signal processing runs server-side.

CHANNEL MODEL
Line-of-sight, specular reflections via the image-source method, knife-edge diffraction, transmission, material attenuation and Doppler.
DIGITAL PATH
QPSK modulation, AWGN and bit-error-rate in a seeded, reproducible pipeline.
SYSTEM DETAIL
render_rx_block/5 runs the Rust NIF on a dirty CPU scheduler with artifact-magic checking, with a deterministic pure-Elixir reference fallback that mirrors its sample order, interpolation, rotation and RNG.
BOUNDARY
A simulator, not a live radio.

DS—02

VISUALISATION

Modulation Studio

A browser DSP visualizer with a live demo. Named modulation schemes are drawn as waveforms, FFT plots and constellations so the effect of a parameter is visible immediately.

SURFACE
Runs in the browser; no install and no server-side DSP.
READOUT
Waveform, frequency spectrum and constellation views of the selected named scheme.
SCOPE
A teaching and inspection tool for named schemes — deliberately not a claim about a fixed catalogue size.

Live demo ↗ Source repository ↗

DS—03

ARCHITECTURE

MoE Memory Wall

A computer-architecture group course project studying Mixtral-8x7B decode with experts offloaded to CPU DRAM, using LLMSimulator and an SSD-offloading variant.

MECHANISM
Training-free expert predictors and a prefetcher that copies predicted experts from DRAM into HBM ahead of use, with guided replacement, preemption and a feedback throttle.
REPORTED RESULT
The authors' calibrated speculative gate reports 1.27× at C=64 on TinyMoE prose against on-demand LRU, with explicit energy and DRAM-to-HBM traffic costs reported alongside it.
BOUNDARY
Simulation only. No GPU measurements were taken.

04 / THINKING

The trace is
the argument.

I trust a model more when I can see what it assumed, and I trust a measurement more when I can reproduce it.

A / 01

Model the boundary

The interesting behaviour lives where a scheduler meets a sample, or where a predicted expert crosses the DRAM–HBM line. Naming that boundary is the first step to measuring it.

A / 02

Label the boundary

A simulator is a simulator. A reported speedup is reported from a specific configuration. Saying exactly what was run is part of the result, not a footnote to it.

A / 03

Keep it local

Local-first tools and on-device inference are not an aesthetic here: they are a way to let a person keep the trace of their own work.
